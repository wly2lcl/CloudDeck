# ADR-0008 商业化与部署分阶段（A → B → C）

- 状态：已接受
- 日期：2026-11-14
- 关联：[ADR-0005](0005-multi-tenancy-billing.md)、[ADR-0006](0006-third-party-agent-compliance.md)

## 背景

需要在「快速验证」「产品化收入」「企业合规」之间取舍。三者对凭据、计费、部署、隔离的要求不同，但并非互斥产品线。

## 决策

采用分阶段路径：

1. **起步 A：自带钥匙的内测版**
   - 仅 BYOK，不做平台 key 池、订阅、发票。
   - 单机 compose 部署，控制面无状态，存储外部化。
   - 目标是验证内容链与媒体流水线的真实价值。

2. **目标 B：创作者 SaaS**
   - 订阅 + 额度 + 超量按量；M3 只实现「额度 + 硬上限」，M5 再补账单与发票。
   - 试用租户可使用平台额度池；正式用户 BYOK 优先。
   - 部署从单机演进到 K8s，runner 与 GPU worker 分节点池。

3. **分支 C：企业私有化**
   - 不单独建产品线，是 B 的一种部署形态：同一套镜像 + 租户配置导出 + 离线部署文档。
   - 仅在出现明确机构客户时投入，不进入主线排期。

## 各决策结论

| 决策 | 结论 | 生效阶段 |
|---|---|---|
| D2 部署 | 单机 compose 起步；控制面无状态 + 托管 Postgres/Redis/S3；M4 迁 K8s | A/B |
| D3 模型渠道 | BYOK 优先；平台池仅内部与试用；`credentials.policy` 按能力声明 | A/B |
| D4 第三方 agent | 首发仅 BYOK；平台代调是否开放，取决于 M3 前完成的条款核对 | A |
| D5 计费 | 订阅 + 额度 + 超量；M3 只做额度与硬上限，M5 补账单/发票 | B |
| D7 沙箱 | 自研 worker 用 Docker；第三方 agent 用 gVisor；coding 场景再评估 Firecracker | A/B |
| D8 视频路线 | 确定性合成优先；生成式模型仅作为单镜头渲染 driver，预算单列 | A/B |

## 闸门

- **M3 商业化闸门**：条款核对结论决定平台 key 池是否对外开放；未通过则维持仅 BYOK。
- **M3 范围闸门**：不实现订阅续费、发票、退款、结转。
- **C 分支闸门**：至少有 1 个付费意向客户，才启动私有化打包。

## 后果

正面：
- M0–M3 不被计费与合规复杂度拖慢
- 架构上预留了 `credentials.policy` 与 `usage_ledger`，A→B 不返工
- C 复用同一代码与镜像，避免三套产品

代价：
- 内测期转化门槛高，用户增长慢
- 平台池与订阅计费推迟，收入验证也推迟
- 私有化支持文档与版本兼容成本在 C 启动时才体现

## 回滚条件

- 若 M3 前已有大量用户要求「开箱即用」，提前评估平台池（需先过条款核对）
- 若 M4 单机容量持续不足且迁移成本上升，提前迁 K8s
- 若私有化需求出现但代码耦合严重，推迟 C 并先补租户配置导出
