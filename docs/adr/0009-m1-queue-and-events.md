# ADR-0009 M1 使用 Postgres 队列与轮询事件流

- 状态：已接受（M1 临时方案）
- 日期：2026-11-14

## 背景

架构文档原定 Redis + BullMQ 作为任务队列、Redis 发布订阅推送 SSE。M1 需要尽快打通「提交 → 执行 → 事件 → 产物」全链路，而 BullMQ 会引入第二套状态（队列里的 job 与数据库里的 job），并产生双写与恢复一致性问题。

## 决策

- 任务队列使用 Postgres `jobs` 表：`status='queued'` + `FOR UPDATE SKIP LOCKED` 原子领取，`lease_until` 防止悬挂。
- 事件流使用 `job_events` 表 + SSE 轮询（300ms），按 `seq` 从 `Last-Event-ID` 补发。
- M1 不引入 Redis；`infra/compose` 中的 Redis 保留但未使用。
- 任务状态与事件在同一数据库事务边界内，避免跨存储不一致。

## 后果

正面：
- 入队与任务记录同事务，不会出现「队列有、库里没有」。
- 断线重连、进程重启、补发都只依赖数据库。
- 测试可用 PGlite 完整跑通，无需外部服务。
- 少一个需要运维的有状态组件。

代价：
- 高频轮询会给数据库增加读压力；M1 的并发规模下可接受。
- 事件延迟上限约 300ms，不适合毫秒级交互。
- 跨区域/多实例扩容时需要重新评估。

## 回滚条件

出现以下任一情况，评估 BullMQ 或 Postgres LISTEN/NOTIFY：
- 轮询 QPS 成为数据库主要负载
- 单租户并发任务 > 50
- 需要跨区域任务分发或毫秒级事件
