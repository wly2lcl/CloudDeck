# ADR-0007 移动端选用 Flutter

- 状态：已接受
- 日期：2026-11-14

## 背景

移动端首版只承担「看进度、听成品、做轻量确认」，但长期会覆盖音频/视频播放、推送、长列表与离线缓存。候选为 Flutter 与 Expo/React Native。

## 决策

移动端使用 Flutter（Dart），Web 仍为 Next.js。

- 客户端 SDK 由 OpenAPI 生成 Dart，禁止手改生成物。
- design token 以 JSON 为单一来源，导出 Dart 常量。
- schema 表单渲染器在 Dart 侧独立实现，与 Web 的渲染器共享同一份 schema。
- 推送用 FCM/APNs，播放用 `just_audio` / `video_player`，缓存用 `drift`。

## 理由

1. 团队已有成熟 Flutter 产品经验（NovelPhone，621 个用例、双端发布流程），交付确定性高。
2. 移动端核心是媒体播放与流畅列表，Flutter 的自绘渲染与播放生态更稳。
3. 一套代码覆盖 Android/iOS，后续可评估桌面端。
4. 移动端范围被刻意收窄，跨语言契约的成本可控。

## 后果

正面：
- 移动端体验与性能一致，减少平台差异 bug
- 复用团队既有的构建、签名、发布流程
- 与 Web 的耦合仅剩 API 契约，边界更清晰

代价：
- 多一套工具链（Flutter SDK、Gradle、Xcode），CI 时间增加
- 无法直接复用 TS 类型/组件，需两条代码生成链并防漂移
- 表单渲染器与资产渲染器双端各实现一次，能力上新需双端回归

缓解：
- CI 增加「生成物未漂移」检查，生成命令与提交产物绑定
- 能力包只允许使用平台内置控件类型，减少双端渲染差异
- 移动端功能清单保持最小，超出清单的需求先评估 Web

## 替代方案

- **Expo/React Native**：类型与组件复用最好、单一 TS 栈，但团队经验与媒体一致性优先级更高。
- **PWA only**：成本最低，但后台播放、推送与离线体验不足，不满足有声书场景。

## 回滚条件

若出现以下情况，重新评估：
- 移动端需求持续超出「进度 + 播放」范围，双端渲染成本高于收益
- Flutter 团队人力无法保障，Web 与移动端发布节奏互相拖累
